# Техническое описание проекта для резюме — QA Automation Engineer

## Проект

Автоматизация тестирования личного кабинета Sminex (web-приложение) и связанных REST API на тестовых окружениях DEV/STAGE. Покрывались ключевые пользовательские сценарии: авторизация по телефону и OTP, выбор проекта, главная страница, пропуска, обращения, счета, приборы учёта, новости и уведомления.

## Стек и архитектура тестируемого web-приложения

Ниже — стек целевого продукта, подтверждённый технической документацией проекта, а не стек тестового фреймворка.

- **Frontend:** React.js; web-клиент ЛК развёрнут отдельно от backend API.
- **Backend:** C#; функциональность разделена на сервисы, в том числе Requests, Finance, Counters, News & Offers, Notifications, Common, Videocameras и Docs.
- **API:** REST/JSON через API Gateway; для DEV используются отдельные URL frontend и API Gateway. Контракты API доступны через Swagger и документированы также в Postman-коллекции.
- **Авторизация и доступы:** Keycloak; вход по телефону и OTP, выдача Bearer access/refresh token, профиль и права пользователя/проекта.
- **Данные:** PostgreSQL; хранилище объектов S3. В документации 1С обозначена как master-система данных для ряда доменов.
- **Интеграции:** 1С (CRM DK, CRM DK Lite, бухгалтерский контур), Kafka и ETL. Через Kafka передаются данные пользователей и доступов, заявок, счетов, показаний счётчиков, новостей, документов и уведомлений; часть операций идёт в обратном направлении из сервисов в 1С.
- **Уведомления:** отдельный сервис Notifications; in-app события поступают через Kafka, а push-уведомления доставляются через Firebase/APNS. Для web-версии в автотестах покрыты InApp-уведомления и интерфейс уведомлений.
- **Внешние сервисы и секреты:** SmsService, HashiCorp Vault.
- **Наблюдаемость:** Grafana для метрик и алертов, OpenSearch для логов.
- **Инфраструктура:** облачное развёртывание, отдельные контуры DEV, preprod и production; GitLab используется для исходного кода frontend/backend и Postman-артефактов.

### Архитектурный контекст для тестирования

Приложение является распределённой системой: пользовательский интерфейс React.js вызывает C#-сервисы через API Gateway, а доменные данные синхронизируются с 1С асинхронно через Kafka и ETL. Поэтому автотесты строились на нескольких уровнях: UI для пользовательского результата, API для контрактов и бизнес-правил, а также перехват сетевых запросов для управляемой проверки UI при недоступном или ограниченном состоянии DEV-данных.

## Роль и результат

QA Automation Engineer: спроектировал и развивал набор из **40 автотестов** на уровнях UI и API, подготовил переиспользуемую тестовую инфраструктуру, профили окружений, механизм авторизации без повторного OTP, сетевые моки и локальный процесс запуска с Allure-отчётностью.

## Реальный технологический стек

- **Язык:** Python.
- **Тестовый фреймворк:** pytest 8.4.1; конфигурация в `pytest.ini`, автосбор тестов из каталога `tests`, подробный traceback, автоматическая очистка результатов Allure перед запуском.
- **UI-автоматизация:** Playwright 1.54.0, синхронный Python API; Chromium запускается через плагин `pytest-playwright`.
- **API-тестирование:** Playwright `APIRequestContext`; отдельный клиент `AuthApi` для запросов авторизации.
- **Отчётность:** `allure-pytest` 2.14.3 и Allure Commandline; шаги, severity, epic/feature/story, текстовые/JSON-вложения и скриншоты.
- **Управление конфигурацией:** `python-dotenv`, `.env.<profile>`, pytest-параметры `--env`, `--phone`, `--refresh-auth`.
- **Инструменты окружения и запуска:** PowerShell-скрипты, virtual environment `.venv`, `requirements.txt`, Git ignore для секретов, кэшей, результатов и файла сессии.

## Что было настроено в тестовом окружении

### Профили стендов и тестовые данные

- Реализована загрузка профиля по имени окружения: `.env.dev`, `.env.stage` и резервный `.env`.
- В переменные окружения вынесены изменяемые параметры: `BASE_URL`, `API_BASE_URL`, `PHONE`, `PROJECT`, `PROJECT_ID`.
- Настроен приоритет конфигурации: параметры pytest и переменные текущей сессии имеют приоритет над файлом профиля; профиль имеет приоритет над `.env`.
- Добавлены pytest-параметры для переключения стенда и тестового пользователя без изменения кода тестов: `--env`, `--phone`.
- Подготовлен `.env.example` без необходимости менять исходный код при подключении нового пользователя или окружения.

### Подготовка авторизованного состояния

- Реализован полный UI-flow авторизации: ввод телефона, согласие с политикой, запрос OTP, получение кода из ответа DEV API, ввод кода, вход и выбор проекта.
- После успешного входа cookies и browser storage сохраняются в `.auth/sminex_ui.json` через `context.storage_state()`.
- Введена session-scoped фикстура `ui_storage_state`: авторизация выполняется один раз за прогон, а не в каждом UI-тесте.
- Реализована проверка актуальности сохранённой сессии. Если она истекла, принудительно обновлена параметром `--refresh-auth` или автоматически создана повторно.
- Добавлена логика переключения на нужный жилой комплекс/проект при валидной сессии, но неверно выбранном проекте.
- Для тестов разделов создана фикстура `authed_page`, которая создаёт изолированный browser context с сохранённым `storage_state`, открывает главную страницу и гарантирует выбранный проект.

### Запуск и результаты тестов

- Подготовлен `scripts/run_suite.ps1`: создаёт служебные каталоги, при необходимости готовит/обновляет авторизационное состояние, запускает выбранный набор в Chromium и сохраняет JUnit XML в `test-results/junit.xml`.
- Подготовлены скрипты `run_with_allure.ps1`, `open_allure.ps1` и обёртка `allure.cmd` для генерации и открытия Allure HTML-отчёта на Windows, включая пути с кириллицей и пробелами.
- В `pytest.ini` настроен вывод результатов в `allure-results` и очистка результатов предыдущего прогона, чтобы отчёты не смешивались.

## Как строились автотесты

### Архитектура

- Использован паттерн **Page Object Model**. Локаторы, действия и проверки экранов изолированы в `pages/`; тесты описывают бизнес-сценарий, а не технические детали DOM.
- Для ключевых разделов созданы отдельные Page Object-классы: авторизация, главная, выбор проекта, пропуска, создание гостевого пропуска, обращения, создание обращения, счета, приборы учёта, новости и уведомления.
- Локаторы преимущественно построены на семантике UI: `get_by_role`, `get_by_text`, `get_by_placeholder`, `get_by_test_id`. Для динамических блоков применялись CSS/XPath и регулярные выражения.
- Повторяемые сквозные действия вынесены в helpers: UI-логин, работа с сохранённой сессией, сетевые перехваты.
- API-вызовы авторизации инкапсулированы в отдельном `AuthApi`; это исключило дублирование URL, заголовков и payload в тестах.

### Уровни и сценарии тестирования

- **API:** позитивный сценарий `send code → token → userInfo`; проверка HTTP-статусов, наличия access/refresh token, типа токена и данных профиля.
- **API-негативы:** невалидный и пустой номер телефона, неверный OTP; проверка точных статусов 400/401 и контракта ошибки `invalid_grant`.
- **UI:** отображение и интерактивность формы входа, переключение вкладок, ввод номера с учётом маски, полный вход, выбор проекта и доступ к главной странице.
- **Функциональные UI-сценарии:** навигация и действия в разделах пропусков, обращений, счетов, приборов учёта, новостей и уведомлений.
- **Интеграционные проверки UI–API:** при открытии приборов учёта проверяется, что запрос к API содержит `PROJECT_ID` из профиля окружения.

### Работа с нестабильностью и зависимостями стенда

- Использованы встроенные автоожидания Playwright (`expect`) и явные timeouts для динамического интерфейса.
- Для полей с масками реализован устойчивый ввод: очистка поля, `Control+A`/`Backspace`, посимвольный ввод через `press_sequentially`.
- Учтены особенности интерфейса: скрытые элементы, tooltip, перехватывающий клик, модальные формы и неустойчивые состояния на DEV; в отдельных точках применены `Escape`, fallback-навигация и `force=True` после проверки видимости.
- Для сценария передачи показаний применено сетевое тестовое управление через Playwright `page.route`:
  - GET `/api/v3/counters` выполняется через `route.fetch`, затем в ответе подменяются период приёма показаний и флаг `readOnly`;
  - POST `/api/v1/counters/{id}/readings` мокируется успешным ответом;
  - payload перехватывается и проверяется: тарифы `T1/T2/T3` и переданное значение.
- Моки позволили изолировать UI-проверку от серверного ограничения проектного интервала, из-за которого реальный DEV backend возвращал 400.

## Методология и практики

- **Layered test approach:** API-тесты проверяют контракт и бизнес-правила авторизации; UI-тесты проверяют пользовательские потоки; отдельные сценарии контролируют связку UI и сетевых запросов.
- **Позитивное и негативное тестирование:** для авторизации проверяются успешный путь, пустые/невалидные данные и неверный OTP с точными ожидаемыми статусами и телом ошибки.
- **Функциональный и интеграционный фокус:** тесты проверяют доступность элементов, навигацию, изменение состояния UI, отправку данных и параметры HTTP-запросов.
- **Изоляция тестов:** каждый `authed_page` получает отдельный browser context, но использует общий валидный `storage_state`; это уменьшает зависимость тестов друг от друга и сокращает обращения к OTP.
- **Поддерживаемость:** общая конфигурация и fixtures находятся в `conftest.py`, UI-детали — в Page Object, сквозные технические операции — в helpers, API — в специализированном клиенте.
- **Наблюдаемость:** каждый тест размечен метаданными Allure; действия описаны через `allure.step`, к проверкам прикладываются скриншоты, URL, тела HTTP-ответов и JSON payload.

## Формулировка для резюме

Разработал и поддерживал UI- и API-автотестов для личного кабинета Sminex: React.js frontend, C# микросервисы за API Gateway, Keycloak, PostgreSQL, интеграции с 1С через Kafka/ETL. Использовал Python, pytest, Playwright и Allure. Настроил параметризуемые DEV/STAGE-профили через dotenv и pytest CLI, подготовил повторно используемую UI-сессию на основе Playwright storage state, что исключило OTP-логин в каждом тесте. Построил Page Object Model, выделил API-клиент авторизации и helpers для сессии/сетевых моков. Реализовал проверки позитивных и негативных API-сценариев, UI-потоков разделов ЛК, передачу показаний с перехватом и валидацией HTTP payload. Автоматизировал локальный запуск набора, JUnit XML и генерацию Allure-отчётов.

## Важное уточнение

В репозитории есть локальная автоматизация запуска, JUnit XML и Allure, но не обнаружена конфигурация CI/CD (например, GitLab CI, GitHub Actions или Jenkinsfile). Поэтому в резюме корректно указывать подготовку тестового окружения и локального процесса запуска/отчётности; интеграцию в CI/CD указывать только если она была выполнена вне этого репозитория.
